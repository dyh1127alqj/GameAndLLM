# GameCore 战斗内核 · 设计符合性审查

- **审查日期**：2026-09-22
- **审查对象**：`src/GameCore` 当前实现（截至 `a6af16c`）与 [BATTLE_CORE.md](../BATTLE_CORE.md)（v2.0，当前唯一有效的战斗规则文档）的逐条对照
- **修改状态**：🔴 待修复
- **说明**：本报告**不重复**编译错误相关内容（见 [2026-09-22_GameCore战斗内核审计_待修复.md](./2026-09-22_GameCore战斗内核审计_待修复.md)、[R2 复审](./2026-09-22_GameCore战斗内核复审_待修复_R2.md)），只关注"代码逻辑即便编译通过，行为是否符合设计文档"这一维度。审查方式：逐条对照 `BATTLE_CORE.md` 第 5~21 节与 `src/GameCore` 实际代码。

## 一、结论摘要

Sprint 1 的目标（据 `ENGINEERING_PLAN_AND_ASSETS.md`）是"建立 Zero-GC 事件环形队列与定点数数学工具"，尚不要求实现元素克制、状态效果、Modifier 挂钩等扩展机制，这部分缺失是**预期内**的，不算违背设计（见第三节）。

但审查发现**治疗管线完全没有接入战斗主循环、技能的目标模式配置被完全忽略、两个核心资源数值（普攻回法量、受击法力退火）与设计文档给出的具体数值不符或完全缺失、ATB 充能速率是设计值的 2 倍**——这几项已经不是"功能未完成"，而是"已实现的代码在做设计文档明确禁止/不同的事情"，会直接导致战斗表现（治疗单位形同虚设、技能节奏、战斗时长）系统性偏离设计预期，建议优先级不低于编译错误本身。

## 二、🔴 实现与设计明确冲突

### 2.1 治疗管线（HealPipeline）从未被 BattleSim 调用

`grep HealPipeline src/GameCore/Battle/BattleSim.cs` 零命中。`BattleSim.CastSkill()`（[BattleSim.cs:114-131](../../src/GameCore/Battle/BattleSim.cs#L114-L131)）对**任何**技能——无论是伤害技能还是设计为治疗的技能——一律调用 `DamagePipeline.CalculateAndApply`。

对照 [BATTLE_CORE.md 11.1](../BATTLE_CORE.md#十一单次出手完整结算管线)：

```
for t in targets:
    if 效果为治疗: ApplyHeal(u, t, ...)
    else:          ApplyDamage(u, t, ...)
```

设计要求按效果类型分流到 `ApplyHeal` / `ApplyDamage` 两条管线（11.2 / 11.3）。当前实现里 `HealPipeline.cs` 存在且有完整测试（`PipelineTests.HealPipeline_Applies_Dual_Multipliers`），但**从未被 `BattleSim` 引用**，是一段孤立的死代码。`SkillDefinition.HealRatioPermille` 字段同样从未被读取。

**实际后果**：`Program.cs` 里配置的"拂尘仙姑"（支援职业，`ss_heal_01` 甘霖普降）技能，因为 `SkillDefinition.DamageRatioPermille` 默认值是 `1000`（未显式覆盖），实际战斗中会被当作**对最近敌人造成 100% Atk 物理伤害的攻击技能**执行，而不是设计意图的"治疗己方血量最低单位"。支援职业在当前实现下完全不能治疗。

### 2.2 技能的 `TargetMode` 配置被完全忽略

`BattleSim.ExecuteTurn()`（[BattleSim.cs:70-97](../../src/GameCore/Battle/BattleSim.cs#L70-L97)）在**判断要放哪个技能之前**就已经用写死的 `TargetMode.Nearest` 从敌方阵营选好了目标：

```csharp
var enemies = u.Faction == Faction.Player ? Context.EnemyTeam : Context.PlayerTeam;
var target = TargetResolver.ResolveTarget(u, TargetMode.Nearest, enemies, _lockTracker);
```

之后无论最终判定放大招、战技还是普攻，都复用这一个目标。`SkillDefinition.TargetMode` 字段（`LowestHpPercentage` / `AllEnemies` 等，[SkillDefinition.cs:26](../../src/GameCore/Model/SkillDefinition.cs#L26)）从未被读取。

对照 [BATTLE_CORE.md 11.1 步骤 2](../BATTLE_CORE.md#十一单次出手完整结算管线)：

```
targetMode = (skill != null) ? skill.TargetMode : Single
targets = ResolveTargets(u, targetMode)
```

设计要求**先确定要放的技能，再按该技能配置的 `TargetMode` 解析目标**。当前实现顺序反了，且目标池永远只在"敌方阵营"里选（`enemies` 变量），这与 2.1 结合会导致：即便日后把 `HealPipeline` 接上，治疗类技能的目标解析依然会从敌人堆里选目标，而不是design要求的"我方 `HpRatio` 最低的存活单位"。

### 2.3 普攻回复法力量与设计值不符（+10 vs 设计 +30）

`BattleSim.ExecuteTurn()` 普攻分支：

```csharp
BasicAttack(u, target);
u.CurrentMana = global::System.Math.Min(100, u.CurrentMana + 10);
u.CurrentRage = global::System.Math.Min(100, u.CurrentRage + 10);
```

对照 [BATTLE_CORE.md 八、资源系统](../BATTLE_CORE.md#八资源系统法力与怒气)：

| 规则 | 设计值 | 实现值 |
|---|:---:|:---:|
| 普攻回法 | **+30** | **+10** |
| 普攻回怒 | +10 | +10 ✅ |

设计明确推导"每 4 次普攻后第 5 次出手放战技"（`0→30→60→90→100`）。当前实现的 +10 会让填满法力需要 **10 次普攻**而不是 4 次——直接把设计文档 [附录 B-7](../BATTLE_CORE.md#b-7-技能系统可能形同虚设) 明确列为"首要验证项"的风险（"技能系统可能形同虚设"）从"需要验证是否会发生"变成"当前实现下必然发生"：20~40 秒的目标战斗时长内，多数单位可能全程一次战技都放不出来。

### 2.4 受击法力退火（Mana Burn，-10）机制完全未实现

`DamagePipeline.CalculateAndApply` 第 6 步（[DamagePipeline.cs:82-87](../../src/GameCore/Pipeline/DamagePipeline.cs#L82-L87)）只写了受击回怒：

```csharp
target.CurrentHp = Math.Max(0, target.CurrentHp - hpToDeduct);
if (target.CurrentHp > 0)
{
    target.CurrentRage = Math.Min(100, target.CurrentRage + 5);
}
```

对照 [BATTLE_CORE.md 8.3 受击法力退火](../BATTLE_CORE.md#83-受击法力退火)：单位受到直接攻击伤害时，`Mana = max(0, Mana - 10)` 应与受击回怒同时触发，两者是并列规则。当前代码里完全没有对 `target.CurrentMana` 做任何扣减——这不是数值不对，是**整条规则都不存在**。这条规则也是设计文档 [附录 B-3](../BATTLE_CORE.md#b-3-前排单位断蓝) 风险分析的前提（"同速下 4 个以上敌人集火会让法力恒为 0"），目前实现下这个风险反而不会发生——但不是因为规则被妥善处理，而是因为规则被漏掉了，前排单位的法力增长速度会显著快于设计预期。

### 2.5 ATB 行动条充能速率是设计值的 2 倍

`BattleSim.AdvanceGauges()`：

```csharp
u.CurrentGauge += (u.BaseSpeed * 1000) / (60 * 100);
```

即 `ΔGauge(每tick, 千分比制) = Speed / 6`。

对照 [BATTLE_CORE.md 7.1 充能公式](../BATTLE_CORE.md#七行动条atb)：

$$\Delta \text{Gauge} = \text{Speed} \times \text{SlowFactor} \times 0.005 \times \Delta t$$

以 `Δt = 1/60`（60Hz 定帧）代入并换算为千分比制：`ΔGauge_permille = Speed × 0.005 × (1/60) × 1000 = Speed / 12`。

**实现值 `Speed/6` 恰好是设计值 `Speed/12` 的 2 倍**。例如设计里 `Speed=200` 的单位应 1 秒（60 tick）充满一条行动条，当前实现下只需 0.5 秒。这会让整场战斗的出手频率、进而技能/大招循环、进而战斗总时长，全部systematically 快了一倍，与设计反复强调的"目标战斗时长 20~40 秒"、"倍速实现铁律"等章节的数值前提直接冲突。

**建议**：`60 * 100` 应改为 `60 * 200`（或等价地把系数从 `1000/(60*100)` 改为 `1000/(60*200)`），使其等于设计的 `Speed/12`。

## 三、🟡 实现与设计有偏差，但影响面较小

### 3.1 星级评定边界：5 人队伍存活 40% 时被误判为 2 星

`BattleResult.StarRating`（[BattleContext.cs:42-54](../../src/GameCore/Battle/BattleContext.cs#L42-L54)）：

```csharp
if (alive == total) return 3;
if (alive >= total / 2) return 2;
return 1;
```

设计（[17.1](../BATTLE_CORE.md#十七胜负判定)）：100% → 3★，50%~80% → 2★，<50% → 1★。对 5 人队伍，`total / 2` 是整数除法结果 `2`，于是存活 2 人（40%）也满足 `alive >= 2`，被判为 2★，但按设计 40% 应为 1★。建议改成按比例浮点比较（`alive / (float)total >= 0.5`）而非整数除法。

### 3.2 伤害缺少"至少造成 1 点"的保底

设计（[11.2 步骤 4](../BATTLE_CORE.md#112-单目标伤害结算)）要求 `final = max(1, floor(final))`。`DamagePipeline.CalculateAndApply` 里 `postArmorDmg` 没有任何下限钳制（[DamagePipeline.cs:48](../../src/GameCore/Pipeline/DamagePipeline.cs#L48)），当攻击力很低、目标护甲很高时可能出现 0 伤害。虽然 `CombatMath.Mul` 会四舍五入，理论上仍可能舍入到 0（例如 `raw` 很小、`armorRatio` 也很小时）。

### 3.3 斩杀（Execute）实现方式与设计架构不同

设计（[21.6](../BATTLE_CORE.md#216-阈值斩杀execute)）要求斩杀通过 `Modifiers.GetExecuteThreshold(src, tgt)` 挂钩返回浮点阈值，默认 `0`（即默认关闭）。当前实现把 12% 这个具体数值和判定逻辑直接硬编码进 `DamagePipeline`，用一个 `bool hasExecutePower` 参数控制开关。Sprint 1 没有 Modifier 系统，这是可以理解的权宜之计，但要记录下来——后续接入 Modifier 体系时这段需要重构，否则会有两套斩杀逻辑并存的风险。

### 3.4 索敌黏性锁（TargetLockTracker）是设计文档里没有的机制

`BATTLE_CORE.md` 第十节"目标选取规则"里没有任何"目标锁定黏性"的描述——设计的默认单体目标规则（10.1）是纯函数式的，每次出手都按规则重新计算，不依赖历史状态（有状态的目标覆盖只有"嘲讽"一种，且是设计明确定义的机制）。当前实现里的 `TargetLockTracker`（1 秒黏滞，避免同排血量拉锯导致目标反复横跳）是代码自行加入的机制，设计文档没有对应章节。不是错误，但建议要么把这个机制正式写进 `BATTLE_CORE.md`，要么确认它是否会导致"确定性回归测试"（[18.4](../BATTLE_CORE.md#184-可复现性检验)）的预期结果和"纯按 `TargetMode` 规则重算"的设计假设不一致。

### 3.5 Gambit 战术指令槽已建模但从未被求值

`UnitSnapshot.TacticsSlot1` / `TacticsSlot2`（[UnitSnapshot.cs:60-61](../../src/GameCore/Model/UnitSnapshot.cs#L60-L61)）字段已经存在，但 `grep TacticsSlot src/GameCore/Battle/BattleSim.cs` 零命中——`ExecuteTurn` 完全没有按 [15.3](../BATTLE_CORE.md#153-战前战术指令系统-gambit--d-04d) "指令槽1→指令槽2→内置默认AI"的顺序求值，直接跳过战术系统用基线 AI（15.1）。这与 2.2 的目标解析问题是同一处代码，一并修的话工作量会小很多。

## 四、🟢 预期内的缺失（Sprint 1 范围外，不算违背设计）

以下机制在设计文档中存在完整章节，但当前实现完全没有涉及。由于 `ENGINEERING_PLAN_AND_ASSETS.md` 里 Sprint 1 的范围明确只是"数学工具 + Zero-GC 事件队列 + 基础伤害/治疗/索敌管线"，这些缺失是合理的分期实现，**不在本轮问题清单内**，仅作记录以便后续排期核对：

- 行军 / 接敌阶段状态机（[五](../BATTLE_CORE.md#五战斗生命周期)）——当前没有 `Marching`/`InContact` Phase，战斗从 tick 1 起直接开始 ATB 充能
- 元素克制系统（[12.1](../BATTLE_CORE.md#121-元素相克)）
- 状态效果体系：眩晕/冰冻/沉默/减速/DOT（[十四](../BATTLE_CORE.md#十四状态效果体系)）
- 硬控递减 DR（[14.5](../BATTLE_CORE.md#145-硬控递减dr--d-24b-9)）
- `Modifier` 挂钩体系与标签系统（[十三](../BATTLE_CORE.md#十三标签与修正器)）
- 护盾 / 生命吸取 / 反射 / 驱散 / 无敌 / 隐匿 / 嘲讽等扩展机制（[二十一](../BATTLE_CORE.md#二十一扩展机制)）——虽然 `UnitSnapshot` 已经预留了 `ShieldHp`/`IsInvincible`/`IsStealthed`/`TauntedByUnitId` 等字段，`DamagePipeline` 也已支持吸血/反伤参数，但 `BattleSim` 当前调用点全部传 `0`，尚未真正驱动
- 事件流里 `RageGain`/`UltimateCast`/`ShieldAbsorb` 等细分事件（[十九](../BATTLE_CORE.md#十九事件流接口)）——当前 `BattleEventQueue` 只有 Damage/Heal/SkillCast/UnitDied 四类

## 五、修复建议（优先级）

1. **先接通治疗管线**（2.1）+ **按 skill.TargetMode 解析目标**（2.2）——这两处是同一段代码（`ExecuteTurn`/`CastSkill`）需要一起重构：应改为"先判定形态与技能 → 再按技能的 `TargetMode` 与是否为治疗类型解析目标池 → 分流到 `DamagePipeline` 或 `HealPipeline`"。
2. 修正普攻回法量 `+10 → +30`（2.3），补上受击法力退火 `-10`（2.4）——这两处都是纯数值/一行逻辑的修改。
3. 修正 ATB 充能系数 `Speed/6 → Speed/12`（2.5）。
4. 上述 4 项修完后，建议立刻跑一次 `BattleSimTests.MonteCarlo_10000_Simulations` 并观察平均战斗时长与人均技能释放次数，因为 2.3/2.5 这两个数值 bug 会同时影响这两个指标，两个 bug 同时修复后战斗节奏会发生较大变化，需要重新校准。
5. 星级边界（3.1）与伤害保底（3.2）可顺手修掉，成本很低。
6. 索敌黏性锁（3.4）建议找设计确认是否要保留，保留的话应补充进 `BATTLE_CORE.md`。
7. Gambit 战术槽（3.5）如果本 Sprint 不打算接入，建议在 `ENGINEERING_PLAN_AND_ASSETS.md` 里明确标注为"Sprint 2 任务"，避免后续误以为 Sprint 1 已经完成 AI 系统。
