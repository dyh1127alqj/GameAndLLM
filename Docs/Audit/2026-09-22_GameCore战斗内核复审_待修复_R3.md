## 三、🔴 仍未修复 / 新引入的问题

### 3.1 编译阻断：`TargetResolver.ResolveTarget` 的空 tracker 分支引用了不存在的方法

```
D:\自研\GameAndLLM\src\GameCore\Targeting\TargetResolver.cs(23,20): error CS0103: 当前上下文中不存在名称"PickBestCandidate"
```

为了兼容 `BattleSim.cs` 的调用签名，本轮新增了一个 `ResolveTarget(attacker, mode, targetPool, tracker = null)` 重载（[TargetResolver.cs:14-26](../../src/GameCore/Targeting/TargetResolver.cs#L14-L26)）。当 `tracker == null` 时，它试图调用 `PickBestCandidate(...)`，但这个方法在整个文件里从未被定义（`grep PickBestCandidate` 全仓库零命中）。

**好消息**：这条分支目前是**死代码**——全仓库所有调用点（`BattleSim.cs` 的 3 处）都会传入非空的 `_lockTracker`，永远走 `tracker != null` 的 `ResolveSingleTarget` 分支。但死代码依然会被编译器检查，所以整个 `GameCore.csproj` 还是编译不过。

**建议**：既然目前没有任何调用方需要"无 tracker"的用法，最省事的做法是直接删掉这个可选参数和 `tracker == null` 分支，把 `tracker` 改为必需参数；如果确实想保留"无 tracker 时退化为无黏性索敌"的能力，则需要把 `ResolveSingleTarget` 里黏性锁定相关的几行抽出来，单独实现一个不依赖 tracker 的排序方法。

### 3.2 新逻辑 bug：治疗技能的目标解析必然落回施法者自己，永远选不中队友

这是本轮**新引入**的问题，编译器发现不了，只能通过读代码 / 跑起来才能发现。

`BattleSim.CastSkill` 里治疗分支（[BattleSim.cs:135-145](../../src/GameCore/Battle/BattleSim.cs#L135-L145)）：

```csharp
if (skill.IsHeal)
{
    var allies = u.Faction == Faction.Player ? Context.PlayerTeam : Context.EnemyTeam;
    var healTarget = TargetResolver.ResolveTarget(u, skill.TargetMode, allies, _lockTracker) ?? u;
    ...
}
```

调用方已经正确地把 `allies`（**同阵营**队友列表）作为目标池传进去了。但它最终落到的 `ResolveSingleTarget`（[TargetResolver.cs:31-65](../../src/GameCore/Targeting/TargetResolver.cs#L31-L65)）内部写死了：

```csharp
var candidates = allUnits
    .Where(u => u.Faction != attacker.Faction && !u.IsDead)   // 只保留"和攻击者不同阵营"的单位
    .ToList();

if (candidates.Count == 0) return null;
```

`ResolveSingleTarget` 是按"传进来的是双方混编花名册，内部自己筛出敌人"的旧假设写的——但现在治疗分支传进去的 `allies` 本来就已经是**同阵营**列表，`Faction != attacker.Faction` 这一过滤条件会把 `allies` 里**每一个**单位都滤掉（因为它们的 `Faction` 全都等于 `attacker.Faction`），`candidates` 恒为空，方法恒返回 `null`。于是 `CastSkill` 里的 `?? u` 兜底每次都会生效，**治疗技能实际上永远在给施法者自己加血，`skill.TargetMode`（`LowestHpPercentage`，本该选中我方血量最低的队友）完全没有机会生效**。

对照 [设计符合性审查 2.1](./2026-09-22_GameCore战斗内核设计符合性审查_待修复.md#21-治疗管线healpipeline从未被-battlesim-调用) 和 [BATTLE_CORE.md 11.3](../BATTLE_CORE.md#十一单次出手完整结算管线)——设计要求治疗目标是"我方 `HpRatio` 最低的存活单位"，当前实现看似接上了 `HealPipeline`，实际效果和"治疗完全没实现"在大多数场景下没有本质区别（除非施法者自己就是全队最低血量，否则永远治不到需要救的队友）。

**根因**：`ResolveSingleTarget` 的"内部自动过滤敌人"假设，与新增的"调用方预先按阵营筛好目标池再传入"用法互相冲突。两条使用路径（`ExecuteBasicAttack`/伤害技能传敌方列表 vs. 治疗技能传我方列表）共用同一个方法，但方法内部只支持前一种假设。

**建议**：`ResolveSingleTarget` 不应该再自行按阵营过滤——调用方（`BattleSim`）已经根据"打敌人"还是"救队友"选好了正确的候选花名册，`TargetResolver` 只需要负责在这份名单里按 `TargetMode` 排序选取即可。建议删除 `Where(u => u.Faction != attacker.Faction)` 这一行，只保留 `!u.IsDead` 过滤；嘲讽/黏性锁定的逻辑不受影响。

**同时注意**：`_lockTracker` 是同一个实例，键是 `attacker.UnitId`。同一个单位既会在普攻时用它锁定敌方目标，也会在放治疗技能时查询同一个 key——两种场景的"黏性目标"语义并不相同（该缓存是否应该按"目标阵营/技能类型"再拆分一层，值得设计确认），本轮改动后这一点还没被处理，只是因为上面的过滤 bug 而暂时没有暴露出来，修完 3.2 后需要一并考虑。

## 五、修复建议（优先级）

1. 删掉 `TargetResolver.cs` 里引用 `PickBestCandidate` 的死代码分支（或补全实现），让 `GameCore.csproj` 先编译通过。
2. 修 `ResolveSingleTarget` 的阵营过滤逻辑（3.2），这是本轮最值得优先处理的问题——因为它会让"治疗管线已接入"这个结论产生误导：编译能过、测试大概率也能过（`PipelineTests` 只测 `HealPipeline.CalculateAndApply` 本身，不测 `BattleSim` 里的目标解析），但实机战斗里治疗职业形同虚设的问题依然存在，只是从"代码层面直接崩"变成了"运行时悄悄跑偏"，更难被发现。
3. 编译通过后，强烈建议给 `BattleSim` 补一条集成测试：构造一个"施法者满蓝、队友残血"的场景，跑一次 `CastSkill`，断言**残血队友**（而不是施法者自己）的 `CurrentHp` 增加了——现有的 `PipelineTests`/`BattleSimTests` 都没有覆盖到"战斗主循环里治疗技能选中队友"这条路径，这也是为什么这个 bug 没有被自动化测试拦下来。
4. 全部修完后跑 `dotnet build && dotnet test`，确认 4 个测试类全绿，再核对 G1 门禁指标（10,000 场 ≤ 3 秒、零 GC、人均技能释放 ≥ 2 次）。
